# 实测报告：Intel Ultra 7 255HX NPU 上跑本地英→中实时翻译

> ## 结论
> ✅ **目标达成**：已实现**只用 Intel NPU** 的英文→中文文本流式翻译。
> - NPU 实测 **97 ms/句，吞吐 10.26 句/秒**（已开 `NPU_TURBO`），译文正确。
> - 已通过 `EXECUTION_DEVICES = NPU` **严格验证推理确实执行在 NPU 上**（非静默回退 CPU）。
> - 全程本地推理，模型为 INT8 量化的 OPUS-MT en→zh（约 112 MB）。
>
> 🔑 **关键突破**：这台机器的 NPU 驱动**对任何动态形状模型都会崩溃**。我把整条管线改造成
> **全静态形状**（无状态 decoder + 因果注意力填充解码），绕开了该缺陷。
>
> 🆕 **NPU 驱动更新后复测**（`1003717` → `1005540`）：静态方案**依然有效且编译更快**，
> 加 `NPU_TURBO` 再提速约 13%；但 KV-cache / LLM 路径仍不可用（详见第 7 节）。

## 2. 核心难题与解决方案

### 2.1 难题：NPU 驱动对动态形状崩溃

| 测试 | 结果 |
|---|---|
| 静态 `[2,4]` 矩阵乘 | ✅ OK |
| 动态 `[-1,4]` 矩阵乘 | ❌ `0xC0000409` 崩溃 |
| Marian encoder 动态形状 | ❌ `0xC0000005` 崩溃 |
| Marian encoder 静态 `[1,128]` | ✅ 1.98s 编译，输出与 CPU 相对误差 **1.9%**（正确） |
| Marian decoder（KV-cache State 动态） | ❌ `0xC0000005` 崩溃 |
| Qwen2.5-0.5B（openvino-genai LLMPipeline，官方 NPU 路径） | ❌ 构建时崩溃 |

**排除法结论**（已完成）：
- ❌ 不是 OpenVINO 版本问题 —— 2025.1 / 2025.3 / 2025.4.1 / 2026.0 / 2026.2.1 / 2026.3.1 **六个版本全部一致崩溃**
- ❌ 不是缓存/沙箱问题 —— `CACHE_DIR` 重定向、`NPU_BYPASS_UMD_CACHING` 共 4 种组合全部崩溃
- ✅ **是驱动过旧** —— 本机驱动 `32.0.100.3717`，日期 **2025-02-06**（落后约 19 个月）

### 2.2 解决方案：把整条管线变成全静态形状

**关键发现**：用 `optimum-cli export openvino --disable-stateful` 导出的 Marian decoder
**没有 KV-cache 输入**，是一个纯函数：

```
(input_ids[1,DL], encoder_attention_mask[1,SL], encoder_hidden_states[1,SL,512]) -> logits[1,DL,V]
```

因此可以：

1. 把所有输入**固定成静态形状**（`DL=64`, `SL=128`）→ NPU 可编译；
2. 用一个**无缓存贪心解码循环**：每步把已生成 token 放入固定长度张量，尾部用 `pad` 填充；
3. **因果注意力保证正确性**：位置 `i` 的 logits 只依赖 `≤ i` 的位置，所以**尾部 padding 不会污染结果**；
4. 每步从 `logits[0, step]` 取 argmax 得到下一个 token。

该方案在 CPU 上的译文与参考实现（带 KV-cache 的常规解码）**逐句完全一致**，证明推导正确；
然后同一份静态模型直接编译到 NPU 即可运行。

代码见 `translate.py` 中的 `StaticPipeline`（约 50 行）。

### 2.3 附带发现：Hy-MT2-1.8B 无法导出（版本互斥）

- Hy-MT2 要求 `transformers>=5.6.0`；`optimum-intel`（最新 2.1.0）要求 `transformers<5.6`，
  且其导出器对 Marian 类模型硬性上限 `4.57.6`：
  `ValueError: ... Maximum required is 4.57.6, got: 5.5.4`
- PyPI 上**没有**支持 transformers 5.6+ 的 optimum-intel 预发布版 → 二者无交集。
- 因此本项目改用 **OPUS-MT en→zh**（专用翻译模型，体量小、INT8 友好、NPU 上更快）。

## 7. NPU 驱动更新后复测

驱动：`32.0.100.3717`（2025-02-06）→ **`1005540`**，NPU 编译器 `393219` → `524291`。
（`SUPPORTED_PROPERTIES` 里新增了 `CACHE_MODE`、`NPU_QDQ_OPTIMIZATION`、
`NPU_COMPILER_DYNAMIC_QUANTIZATION` 等，确认驱动/插件栈确实换了。）

### 7.1 逐项结论

| 项目 | 旧驱动 | 新驱动 |
|---|---|---|
| 静态形状（无状态 decoder 方案） | ✅ 111 ms/句 | ✅ **97 ms/句**（编译 6.75s→4.2s，且 `NPU_TURBO` 使 decoder 单步 20.5ms→11.3ms） |
| 无边界动态形状（`[-1,4]`） | ❌ 硬崩溃 `0xC0000409` | ✅ 不再崩溃，改为**正常报错**要求给出边界 |
| **带边界**动态形状（如 `[?..16,4]`，简单算子） | ❌ 崩溃 | ✅ **可用**（batch 2/5/8 正常推理） |
| 真实 transformer + 动态 seq（Marian encoder `[1,1..128]`） | ❌ 崩溃 | ❌ 仍崩溃：`non broadcastable dimensions pair '128' and 1024'` |
| stateful decoder（KV-cache State）+ 静态形状 | ❌ 崩溃 | ❌ 仍编译失败（改为正常报错） |
| openvino-genai LLM（Qwen2.5-0.5B int4） | ❌ 崩溃 | ❌ 明确报错：**NPU37XX 不支持 u4 反量化** |
| openvino-genai LLM（同款 **int8** 重导） | — | ❌ `FeasibleAllocation Pass failed`（attention Select/Slice 的别名分析缺陷），换 3 组形状均同 |

### 7.2 根因认识（比驱动版本更深一层）

`DEVICE_ARCHITECTURE = 3720` —— **255HX 虽是 Arrow Lake，其 NPU tile 用的仍是 Meteor Lake
那一代的 NPU3720（13 TOPS）**，不是 Lunar Lake 的新一代 NPU40XX。这一代的 NPU 编译器对
"KV-cache 状态图 / LLM 典型算子" 的支持很弱，与本机驱动新旧无关。因此：

- **全静态形状的无状态解码，是目前这块 NPU 上唯一稳妥的翻译推理方式**（本项目已实现）；
- LLM 路径（`openvino-genai`）在 NPU3720 上暂时走不通，需等编译器成熟或换 NPU40XX 机型。

### 7.3 对主方案的影响

- `translate.py --device NPU` 在新驱动下**照常工作且更快**（97 ms/句、编译提速 ~38%）。
- `translate.py` 已默认给 NPU 加 `NPU_TURBO=YES`（实测 decoder 单步 -45%）。
- 若以后驱动/编译器更新，可直接复测：
  - `python _dec_stateful_static.py`（stateful decoder 静态形状能否编译）
  - `python _llm_npu_test.py --model models\qwen25-05b-int8-ov --device NPU --bench`（LLM 路径）
- `models\qwen25-05b-int4-ov\` 与 `models\qwen25-05b-int8-ov\` 是 LLM 路径诊断产物，
  当前用不到（共约 820MB），可自行删除；将来若 LLM 路径打通，可用一条命令重新生成。

## 8. 多模型支持（新增）

### 8.1 已接入的两个模型

| 模型 ID | 说明 | 体积 | 质量 | 速度 | 语言码 |
|---|---|---|---|---|---|
| `opus-mt-en-zh` | OPUS-MT 英→中（默认，随包提供） | 112MB | 2/5 | 5/5 | 不需要 |
| `nllb-200-600m` | NLLB-200 distilled 600M | 620MB | 4/5 | 2/5 | `eng_Latn` → `zho_Hans` |

两个模型都**导出为两个变体**：带 KV-cache（CPU/GPU）与无状态全静态（NPU 必需）。

### 8.2 NPU 上的实测性能（本机）

| 模型 | 设备 | 编译/加载 | 平均延迟 | 译文样例 |
|---|---|---|---|---|
| OPUS-MT | NPU（静态） | 约 5 s | **约 106 ms/句** | 你好,你今天好吗? |
| **NLLB-600M** | **NPU（静态）** | **约 30 s** | **约 850 ms/句** | 你好,你今天怎么样? |
| NLLB-600M | CPU（KV-cache） | 1.3 s | 约 178 ms/句 | 你好,你今天怎么样?（与 NPU 一致） |

两种设备上 NLLB 的译文完全一致，说明静态管线转换没有引入偏差。

### 8.3 NLLB 静态解码的两个关键点（踩坑记录）

1. **起始 token 必须是两个**：`[decoder_start_token_id, 目标语言码]`。
   - 只给语言码 → 输出 95 个 `<unk>`（空译文）
   - 只给 `decoder_start` → 退化成土耳其语（`Merhaba, bugün nasılsın?`）
   - 正确写法 → `你好,你今天怎么样?`
2. **从最后一个真实位置读 logits**：起始序列有多长，第一次取 argmax 的下标就是 `len(start_ids)-1`。
   Marian 只有一个起始 token，所以两种写法等价，掩盖了这个差异。

### 8.4 NPU 驱动的硬限制：同一进程内无法换模型

实测结论（这是本次最耗时的排查）：

```
ZE_RESULT_ERROR_INVALID_NATIVE_BINARY, code 0x7800000f
native binary is not supported by the device. BufferInfo already exists at requested index
```

- 单独运行 OPUS 或 NLLB 都正常；**一旦在同一进程里先跑过一个模型，再编译并运行第二个模型就必然报此错**。
- 先 `del` + `gc.collect()` 释放旧管线**不能**可靠解决（有时可行、有时失败）。
- 与线程无关（把编译和推理都放到主线程仍会失败）。

**规避方案（已实现）**：切换模型时**换进程**——
服务写入 `restart.flag` 后退出；`start_server.bat` 检测到该标记就用新模型自动重启；
插件侧则通过 Native Messaging 宿主重新拉起服务（启动时读取 `settings.json` 中的模型）。
实测切换耗时：OPUS→NLLB 约 11 s（含 NPU 编译），全程无需人工干预。

### 8.5 另一处踩坑：端口复用导致的"僵尸服务"

`ThreadingHTTPServer` 默认 `allow_reuse_address = 1`，在 Windows 上**允许两个进程绑定同一端口**，
于是旧实例与新实例静默共存、请求被随机分发（排查时被此现象误导了很久）。
已在 `server.py` 中改为 `allow_reuse_address = False`，第二个实例会直接报"端口被占用"并退出。

## 9. 启动速度与内存优化（2026-11 复测）

用户反馈："拉起服务太慢，而且一启动就吃掉 4G 内存"。定位到三个真实原因，逐项修掉了。

### 9.1 病根一：`import transformers` 就要 4~20 秒

服务只用 tokenizer 把文本换成 id，却为此拖上了整个 transformers（连带 optimum/torch 的探测）。
实测（`_scratch/20261109-perf/probe_startup.py`）：

| 阶段 | 耗时 | 内存变化 |
|---|---|---|
| import numpy + openvino | 0.31 s | +34 MB |
| **import transformers** | **4~20 s**（冷启动首次 20.0 s，之后 3.9 s） | **+322 MB RSS / +930 MB 提交** |
| 其余（本项目的模块） | 0.02 s | ~0 |

**改法**：彻底不用 transformers，换成两条零依赖路径（都已逐 token 与 HF 对齐）：
1. **OpenVINO 预导出 tokenizer 图**（`openvino_tokenizer.xml`，NLLB 目录本来就有）——0.05 s；
2. **SentencePiece + `vocab.json`** 手工复刻 MarianTokenizer（OPUS-MT 用）——0.05 s。

编码结果与 HF 完全一致（`_scratch/20261109-perf/probe_tok.py` 逐条比对 `match=True`），
译文也一致。新增 `prepare_tokenizer.py` 可把任意模型的 HF tokenizer 转成 OV 图。

### 9.2 病根二：监听端口要等模型编译完才绑

以前的顺序是「编译 → 绑端口 → 开始服务」，插件在编译期间连不上，用户看到的是几十秒空白。
现在改成 **先绑端口**（`/health` 立刻返回 `ready:false`）→ 再编译模型 → `ready:true`。
插件可以在加载期间就显示"正在加载模型"，而不是卡在"连接失败"。

### 9.3 病根三：NLLB-600M 在 NPU 上就是又慢又占内存

NPU 全静态管线要**每一步重算整段**（没有 KV-cache），而这台机器的 NPU 是
**NPU3720（13 TOPS）**，256k 词表的 NLLB 在上面非常吃亏。实测：

| 模型 | 设备 | 编译/加载 | 单句延迟 | 进程 RSS |
|---|---|---|---|---|
| OPUS-MT | NPU | **0.5 s** | 197 ms | **702 MB** |
| OPUS-MT | CPU | 0.8 s | 192 ms | 366 MB |
| NLLB-600M | **NPU** | **43 s** | **1832 ms** | **4455 MB** |
| NLLB-600M | CPU | 1.6 s | 2206 ms | 1625 MB |
| NLLB-600M | GPU.0（iGPU） | 9.9 s | 2042 ms | 2030 MB |

**结论**：NLLB-600M 在 NPU 上是"4GB 内存 + 46 秒启动 + 1.8 秒/句"，是这次投诉的全部来源。
默认模型已改为 **OPUS-MT（NPU）**：**启动 1.46 秒、常驻 700MB、每句 131 ms**。

> NLLB 仍然保留可选；只是它更适合 CPU 的带缓存路径（约 178 ms/句），
> 而那条路径要 optimum+torch，与"启动快、内存小"冲突，所以没有设为默认。

### 9.4 顺手拿掉的两块开销

1. **NPU 编译缓存**：`ov.Core().set_property({"CACHE_DIR": "ov_cache"})`，
   二次启动直接导入编译结果（OPUS：5~7 s → 0.35 s）。
2. **编译完立刻丢掉 IR**：`del enc, dec; gc.collect()`，否则 NPU 上会同时存在
   原始权重与编译产物，白占 1~2 GB。

### 9.5 关于本机的两块 GPU（重要发现）

```
CPU    | Intel(R) Core(TM) Ultra 7 255HX
GPU.0  | Intel(R) Graphics (iGPU)
GPU.1  | NVIDIA GeForce RTX 5060 Laptop GPU (dGPU)   ← OpenVINO 通过 Intel GPU 插件的 OpenCL 认到
NPU    | Intel(R) AI Boost (3720)
```

`GPU.1` 能跑通，但**结果不可靠**：同一组句子里出现 4.5 s 的离群值，且译文错乱
（`The quick brown fox...` → "跳"）。它是 Intel GPU 插件借 NVIDIA 的 OpenCL 驱动跑出来的，
不是官方 CUDA 后端。**不要用它跑翻译**。真正可用的是 `llama.cpp` 的 CUDA 构建（见 §10）。

### 9.6 优化前后对照（同一台机器、同一份配置）

## 10. 接入 B 站 Index-Translate（GGUF + llama.cpp）

### 10.1 为什么绕开 OpenVINO 直接跑 GGUF

`IndexTeam/Index-Translate-2B` 是 **Qwen3.5 底座**，`config.json` 里写着
`architectures: ["Qwen3_5ForConditionalGeneration"]`，而且 24 层里有 18 层是
`linear_attention`（线性注意力/mamba 类混合结构）。这带来两个后果：

| 路径 | 结果 |
|---|---|
| `transformers` 直接加载 | ❌ 本机 4.57.6 **没有 qwen3_5** 实现 |
| `optimum-intel` 导出 OpenVINO | ❌ 依赖上面的 transformers |
| `openvino_genai.LLMPipeline` 直接吃 GGUF | ❌ 报 `invalid unordered_map key`：GenAI 的 GGUF 读取器里**没有 `qwen35` 这个架构**（DLL 里 0 次命中） |
| **llama.cpp** | ✅ GGUF 就是它造的，原生支持 |

所以走 llama.cpp：`llama-server.exe` 起一个独立进程（OpenAI/`/completion` 兼容接口），
我们的服务把请求转发过去。**这也顺带解决了内存问题**——不用时把这个进程关掉即可，
和 NPU 上的 OpenVINO 管线互不干扰。

### 10.3 怎么选

| 场景 | 推荐模型 | 理由 |
|---|---|---|
| 整页翻译、日常浏览 | **OPUS-MT（NPU）** | 131 ms/句，100 段约 15 秒 |
| 选中段落、要质量 | **Index-Translate-2B** | 0.7 s/句，质量接近在线翻译 |
| 要中文更自然、肯等 | NLLB-600M（CPU） | 178 ms/句，但需 optimum+torch |

插件里点模型下拉框即可切换，不用改配置。

### 10.4 NPU 跑不了 2B 大模型的原因

不是驱动问题，是硬件代际：这块 NPU 是 **3720（13 TOPS）**，
且编译器对 LLM 的 KV-cache 算子支持很弱（§7.2 已有完整实测）。
2B 模型每生成一个 token 都要把 1.2 GB 权重过一遍内存，NPU 的带宽根本喂不饱。
**要 NPU 上跑 LLM，得等 NPU40XX 级别的新机型。**
